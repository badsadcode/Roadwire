# Roadwire — Product, Architecture & Development Specification

## 1. Project Summary

**Roadwire** is an external AI-powered radio companion for driving games.

It runs independently from the game and creates the illusion of a persistent world of radio users existing beyond the player’s vehicle.

Roadwire is not initially intended to modify or directly integrate with the game executable.

Its primary interaction method is audio:

- player speaks using configurable global Push-To-Talk hotkeys
- speech is transcribed
- simulated characters respond
- dialogue is generated by an LLM
- character-specific voices are generated through TTS
- audio is processed to sound like CB or broadcast radio
- generated audio is played through the user's configured Windows output device

The first intended Roadwire package is:

**Motor Town: Behind The Wheel**

The Roadwire Core must remain sufficiently generic to support other driving games later.

Possible future packages:

- Euro Truck Simulator 2
- American Truck Simulator
- Driving Life
- other driving / trucking / transportation games

---

# 2. Fundamental Architecture

Roadwire consists of three conceptual layers:

```text
ROADWIRE CORE
↓
ROADWIRE PACKAGE
↓
ROADWIRE WORLD
```

## Roadwire Core

The application / simulation engine.

It handles:

- world simulation
- event scheduling
- characters
- memories
- relationships
- radio channels
- conversations
- global hotkeys
- STT
- LLM communication
- TTS
- audio playback
- save/load
- provider configuration
- package loading

## Roadwire Package

Defines what can exist in a particular setting or game.

Example:

```text
MotorTown.roadpack
```

A package may define:

- locations
- cargo
- activities
- event categories
- world rules
- driver archetypes
- characters
- broadcasters
- radio channels
- vocabulary
- prompts
- voices
- player identity generation rules
- simulation defaults

## Roadwire World

A persistent simulation instance created from a package.

A world is effectively a Roadwire save game.

Example:

```text
Package:
Motor Town

World:
Dusty's Main World
```

The package defines possibility.

The world records reality.

---

# 3. Core Design Goal

Roadwire should not feel like:

> an AI chatbot pretending to be a trucker.

It should feel like:

> a radio connected to a world that continues to exist around the player.

The core design philosophy is:

**Roadwire simulates reality.  
AI improvises within that reality.**

The AI is allowed creativity.

However, it must not have unrestricted authority over world state.

---

# 4. AI Roles

Roadwire uses AI for several distinct roles.

They may use the same underlying model with different prompts.

## 4.1 Dialogue Actor

The Dialogue Actor generates spoken dialogue.

It receives:

- character identity
- personality
- current situation
- relevant world knowledge
- recent conversation
- conversational intent

It returns:

```text
spoken dialogue only
```

It does not directly:

- write database state
- start events
- schedule events
- alter memories
- change relationships
- select voices
- play audio

---

## 4.2 World Director

The World Director helps create emergent world events.

It is periodically called as a background task.

It receives:

- current package rules
- current world state
- current characters
- recent events
- active event categories
- severity limits
- package constraints

It generates potential future events.

These are **event candidates**, not immediate world truth.

Example:

```json
{
  "type": "vehicle_issue",
  "actors": ["Bear"],
  "summary": "Bear notices a slow leak in one rear tire.",
  "severity": 2,
  "earliest_start_minutes": 20,
  "expiry_minutes": 180,
  "activation_probability": 0.35
}
```

Roadwire validates the proposal.

If valid, it enters the event candidate pool.

Roadwire may later activate it.

It may also expire unused.

---

# 5. Controlled AI Decision-Making

The LLM may have decision capabilities, but only inside boundaries defined by Roadwire and the active package.

The World Director may decide:

- event details
- plausible actors
- minor consequences
- duration suggestions
- event flavor
- whether an event might be radio-worthy
- possible event continuation
- small social situations
- mundane complications

The World Director should NOT have unrestricted power to redefine the world.

Example package constraints:

```text
Allowed:
- traffic
- deliveries
- cargo
- road conditions
- vehicle issues
- roadside stops
- minor police situations
- social encounters
- weather complications
- breaks
- shift changes

Forbidden:
- supernatural events
- impossible technology
- mass disasters
- character death unless package explicitly permits it
- world-changing events unless package explicitly permits them
```

---

# 6. Event Sources

Roadwire should support three event sources.

## Procedural Events

Generated through deterministic / probabilistic simulation rules.

Examples:

- job completed
- unloading
- fueling
- break
- new job
- shift ending
- driving empty

These provide structure.

## Authored Package Events

Events predefined by the package author.

Examples:

- ferry delay
- specific road closure
- weigh station issue
- local road hazard
- game-specific destination event

These provide setting-specific identity.

## AI-Generated Events

Generated periodically by the World Director.

Examples:

- loose tarp
- paperwork delay
- minor air leak
- driver stopping to help someone
- unusual cargo discussion
- minor roadside situation

These provide variety.

---

# 7. Event Candidate Pool

The World Director should generate future possibilities in the background.

Roadwire maintains a pool of candidates.

Example:

```text
Target candidate pool:
20

Current:
14

Generate:
6 new candidates
```

The pool may be divided by category:

```text
mundane        8
social         4
job-related    4
road-related   2
vehicle        1
unusual        1
```

This prevents AI generation from drifting toward constant disasters.

Candidate states:

```text
GENERATED
↓
VALIDATED
↓
AVAILABLE
↓
ACTIVE
↓
RESOLVED
```

Alternative:

```text
AVAILABLE
↓
EXPIRED
```

Not every generated event happens.

That is intentional.

---

# 8. Event Validation

Before an AI-generated event becomes available, Roadwire validates it.

Validation may check:

- characters exist
- actors are currently compatible with event
- locations exist
- duration is legal
- severity is permitted
- event category is allowed
- no contradiction with current state
- cooldown rules
- repetition limits
- package rules
- required dependencies

Invalid events are rejected.

# 9. World Persistence

Roadwire supports persistent worlds.

When starting Roadwire with a package, the player chooses:

```text
Continue World
New World
```

## Continue World

Loads:

- current character states
- relationships
- memories
- world time
- event candidates
- active events
- recent world history
- broadcaster state
- radio configuration
- simulation seed
- player identity
- recent conversations if required

## New World

Creates:

- new world state
- new simulation seed
- empty history
- default or randomized relationships
- fresh event pool
- new player identity setup
- newly initialized character states

# 16. Time Simulation

The backend owns elapsed time.

The LLM does not simulate passing time itself.

Roadwire maintains:

```text
world_time
last_update_time
elapsed_time
```

When Roadwire is running:

```text
update world
update activities
update event eligibility
update radio availability
```

When Roadwire was closed:

```text
calculate elapsed time
advance world logically
```

Do not replay every missed minute.

Example:

Roadwire closes at:

```text
19:00
```

Roadwire opens at:

```text
08:00 next day
```

It may infer:

```text
Bear finished shift
went home
slept
started next shift
```

---

# 17. Semantic Time

Exact clock time should usually not be passed directly to dialogue generation.

Bad:

```text
TIME:
08:35
```

This encourages unnatural speech.

Instead convert time into semantic context:

```text
time_period:
morning

shift_stage:
early

traffic_state:
quiet
```

The Dialogue Actor treats this as background only.

---

# 18. Character Knowledge

Characters must not automatically know everything.

Knowledge is character-specific.

Types:

## Common Knowledge

Facts all relevant characters may know.

Example:

```text
The port exists.
The quarry road is steep.
Channel 19 is commonly used by drivers.
```

## Personal Knowledge

Character-specific facts.

Example:

```text
Bear knows Dusty usually drives at night.
```

## Heard Knowledge

Information heard over radio.

Example:

```text
Maggie heard Dusty say he was heading south.
```

## Second-Hand Knowledge

Information received from another character.

Example:

```text
Bear heard from Maggie that Dusty had a flat tire.
```

Second-hand knowledge may have reduced confidence.

---

# 19. Hearing a Transmission

Roadwire decides who heard a radio call.

Factors:

- character online
- character tuned to channel
- radio enabled
- attention level
- current activity
- whether directly addressed
- conversation involvement
- interference / future radio rules
- probability

Example:

```python
if online and same_channel:
    chance = attention

    if directly_addressed:
        chance += direct_call_bonus

    if random() < chance:
        heard = True
```

---

# 20. Direct Calls

The player may call a specific simulated driver by:

- name
- callsign
- alias

Examples:

> “Bear, you out there?”

> “Breaker for Maggie.”

> “Rook, come back.”

Roadwire performs:

1. STT
2. name / callsign detection
3. fuzzy matching
4. world lookup
5. availability check

If matched:

```text
target = Bear
intent = direct_call
```

If Bear is unavailable:

```text
silence
```

Roadwire must not magically summon characters.

---

# 21. General CB Calls

Example:

> “Anybody out there?”

or:

> “Mobilki mobilki, co u was słychać?”

Roadwire determines which eligible character may answer.

The LLM does not choose the responder.

Potential responder score:

```text
talkativeness
+ relationship bonus
+ availability
+ boredom
+ relevance
- cooldown
- recent speaker penalty
- busy penalty
```

Selection uses weighted randomness.

Do not always choose the highest scorer.

---

# 22. Number of Responses

Not every general call must receive a reply.

Suggested approximate defaults:

```text
0 replies    10%
1 reply      75%
2 replies    13%
3 replies     2%
```

Actual probability depends on:

- online driver count
- current channel
- world time
- relationship
- radio traffic
- type of player call

---

# 23. Conversation State

Example:

```text

ACTIVE

3

```

# 24. Conversation Context

Recent active conversation remains temporarily available.

Suggested:

```text
6–10 turns
```

Example:

```text
Dusty:
How's it going?

Bear:
Can't complain.

Dusty:
Heading south later?
```

This temporary conversation context should normally remain in RAM or temporary storage.

It should not automatically become long-term memory.

---

# 25. Conversation Lifecycle

AI systems tend to keep conversations alive forever.

Roadwire must explicitly manage when conversations end.

Conversation states:

```text
ACTIVE
WINDING_DOWN
CLOSED
```

Roadwire may maintain:

```text
conversation_energy
```

Energy decreases based on:

- number of turns
- repeated acknowledgements
- no new information
- character personality
- character patience
- long pauses
- sign-off language
- character current activity
- explicit goodbye

---

# 26. Conversation Ending

When a conversation should end, the Dialogue Actor receives:

```text
INTENT:
End the conversation naturally.

Do not ask another question.
Do not introduce a new topic.
Do not invite another response.
Keep it brief.
```

Example response:

> “Alright, drive safe, Dusty.”

Roadwire then marks:

```text
CLOSED
```

If the player replies:

> “You too.”

Roadwire may classify that as:

```text
terminal acknowledgement
```

No further AI response is required.

# 29. Memory

Permanent character memory should remain deliberately small.

Suggested:

```text
8–20 slots per character
```

Memory should contain meaningful facts only.

Example:

```text
Dusty helped Bear during a breakdown.
Dusty often drives southern routes.
Maggie thinks Dusty is funny.
```

Avoid recording trivial history.

Bad:

```text
Dusty said hello at 08:42.
Bear drank coffee.
```

---

# 30. Memory Classes

Initial implementation may use:

## Short-Term Memory

Approximately:

```text
10–15 slots
```

Frequently replaced.

## Core Memory

Approximately:

```text
3–5 slots
```

Meaningful persistent relationship facts.

---

# 31. Memory Eviction

When capacity is exceeded:

```text
delete lowest-value memory
```

Possible scoring:

```text
importance
+ relationship relevance
+ recency
+ repetition
```

Old insignificant memories disappear.

This is intentional.

Characters should forget things.

---

# 32. Conversation Memory Extraction

When an active conversation ends, Roadwire may optionally perform a small extraction.

Question:

```text
Did anything happen in this conversation that deserves persistent memory?
```

Possible response:

```text
Dusty plans to buy a larger truck.
```

or:

```text
NONE
```

Only meaningful information enters memory.

# 33. Dialogue Context Model

Every dialogue request should conceptually separate:

```text
WORLD STATE

CHARACTER STATE

CHARACTER KNOWLEDGE

RECENT CONVERSATION

CONVERSATIONAL INTENT
```

Example:

```text
CHARACTER:
Bear

PERSONALITY:
dry

STATE:

mildly bored

KNOWLEDGE:
Dusty mentioned heading toward the port earlier

CONVERSATION:
Dusty: "Anybody awake out there?"

INTENT:
Respond casually to a general call
```

---

# 34. Context Is Not a Script

This is one of Roadwire’s most important rules:

**Simulation information is context, not dialogue instructions.**

If Roadwire supplies:

```text
Bear is hauling lumber.
Morning.
Traffic is busy.
Dusty is heading south.
```

the Dialogue Actor does not have to mention any of those facts.

If Dusty says:

> “How you doing?”

Bear may simply answer:

> “Can't complain. You?”

The simulated world should make dialogue grounded.

It must not make dialogue feel scripted.

---

# 35. Permanent Dialogue System Prompt

Conceptual permanent prompt:

```text
You generate natural spoken dialogue for characters in a simulated radio world.

You are an actor, not the world simulator.

Use the supplied character identity, state, knowledge, recent conversation and conversational intent.

Treat supplied context as background knowledge.

Do not summarize the supplied context.

Do not mention facts simply because they were provided.

Use only information that naturally belongs in the current utterance.

Keep CB communication concise.

Do not repeatedly greet the player.

Do not repeatedly use names.

Do not announce the exact time unless naturally necessary.

Do not force the character's current activity into every reply.

Do not ask a question simply to keep the conversation alive.

If instructed to close a conversation, end naturally without opening another topic.

Do not invent major world facts.

Minor natural conversational filler is allowed.

Return spoken dialogue only.
```

# 36. CB Mode

CB Mode is optimized for short, responsive interaction.

Features:

- multiple drivers
- global PTT
- channels
- short messages
- spontaneous chatter
- direct calls
- general calls
- conversations
- NPC-to-NPC conversation
- character memory
- individual knowledge
- event-driven calls
- casual non-event conversation
- channel occupancy
- radio listening rules

Typical response:

```text
5–30 words
```

Typical maximum:

```text
1–3 short sentences
```

Low latency is a high priority.

---

# 37. Spontaneous CB Chatter

Roadwire periodically determines whether any character has a reason to transmit.

Possible reasons:

- active world event
- boredom
- social interaction
- warning
- traffic information
- current job frustration
- casual check-in
- responding to another NPC
- generated social event

The character’s current event is optional conversational material.

It is not always the subject.

---

# 38. Broadcaster Mode

Broadcaster Mode is separate from CB Mode.

It simulates:

- radio station
- pirate broadcaster
- talk show
- podcast
- DJ
- call-in program

Characteristics:

- one primary host
- longer output
- structured or semi-structured segments
- optional player calls
- persistent personality
- broadcaster memory
- topic pools
- lower sensitivity to startup latency
- continuous text / audio pipeline

# 40. Broadcaster Generation Pipeline

Broadcaster output may run incrementally:

```text
Generate first text chunk
↓
TTS
↓
start playback
```

While playback occurs:

```text
generate next chunk
↓
generate TTS
↓
queue audio
```

Pipeline:

```text
LLM
↓
text chunk queue
↓
TTS
↓
audio queue
↓
playback
```

As long as generation stays ahead of playback, local model latency becomes less noticeable.

# 45. Local LLM

Roadwire should use local LLMs as plain generation services.

Avoid autonomous agent frameworks.

The local model does not need:

- filesystem access
- shell access
- tool execution
- application permissions
- database permissions

Preferred interaction:

```text
Roadwire
↓
local HTTP API
↓
LLM
↓
plain response
```

An OpenAI-compatible API interface is desirable.

# 58. History Retention

World history should not grow indefinitely.

Resolved trivial events may eventually be deleted.

Example:

```text
Bear bought coffee.
```

May disappear.

Meaningful events may become:

```text
memory
relationship change
world fact
```

Example:

```text
Dusty helped Bear during a breakdown.
```

The raw event may later disappear while the memory remains.

# 74. Product Principle

The key Roadwire principle is:

**The world should influence conversation without controlling conversation.**

World events create context.

Memory creates continuity.

Personality creates character.

Randomness creates unpredictability.

AI creates variation.

Roadwire decides what becomes real.

---

# 75. Final Vision

Roadwire should make a player driving alone feel as though there are other people somewhere beyond the windshield.

Some are working.

Some are bored.

Some are listening.

Some are not.

Some know the player.

Some have never heard of them.

Some remember what happened yesterday.

Some already forgot.

Occasionally something happens in their lives.

Sometimes they talk about it.

Sometimes they just say:

> “Yeah, I'm here. What's up?”

That illusion of a persistent world is the product.
